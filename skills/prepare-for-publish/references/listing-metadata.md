# Listing metadata

## Description

- describe what the add-on does for the user, not how it is built
- avoid the word "plugin" anywhere in product-facing text
- name the primary user problem and the primary outcome

## Release notes

- one short paragraph or a bullet list focused on what changed for users
- avoid internal terminology, ticket IDs, or refactor-only entries
- if a change affects pricing, login, or supported documents, say so explicitly

## Screenshots and assets

- at least one screenshot per primary flow
- regenerate screenshots when panel UI changes meaningfully
- avoid placeholder content that looks like real user data

## Testing information

- list step-by-step actions a reviewer should take
- include any required credentials or sample documents
- call out features that depend on specific document types, such as presentations

## Final pass

- open the listing as if you were a new user
- ask: does this clearly explain what it does, who it is for, and how to use it
- if any of those is unclear, fix it before submitting
